CASE · 01 · PROBLEM

The problem

TEMPORARY DEVICES, TRACKED

Employees sometimes need a temporary device: their laptop is in for repair, they are travelling, or they have just joined and their equipment has not arrived. The request has to be approved, a device has to be found and handed over, and someone has to notice when it is not returned.

I built that process twice. The first build uses the platform’s configuration tools, the way an administrator would. The second is a scoped application where the rules live in scripts, the way a developer would build it.

CASE · 02 · BUILD 1

Infinity Loaner Program

BUILD 01 · ADMIN · CSA BLUEPRINT · GLOBAL SCOPE

Data model

A Loaner Request table (u_loaner_request) that extends Task, with its own LNR numbering. Number is read-only on this table only, through a dictionary override, so Task and its other child tables are untouched.

Request form

A catalog record producer, Request a Loaner Device. A catalog client script limits the device models to the ones allowed for the request type: Standard gets the Infinity HHD, Executive gets the HHD Pro.

Approval

A Workflow Studio flow runs when a request is created: it asks for approval, then moves the request to Work in Progress, or to Closed Incomplete if it is rejected.

Fulfilment

A Visual Task Board with one lane per state; dragging a card updates the record. Notifications go out when a request is created and when it is assigned.

Reporting

An operations dashboard with totals, overdue loans, and requests by priority, device model, state and assignee.

Security

Requesters can read only the requests they opened. Only itil users can change the device model, and a Deny-Unless ACL locks a request once it is closed.

Device data

The device inventory comes in from a CSV through an import set and transform map. It coalesces on serial number, so a re-import updates existing devices instead of duplicating them.

CMDB

A device CI is related to the Email service it depends on, so the dependency view shows what a missing device affects.

CASE · 03 · BUILD 2

Loaner Tracker

BUILD 02 · DEVELOPER · CAD BLUEPRINT · SCOPED APP

Scoped app

Its own scope and a Loaner Request table that extends Task, numbered LTR, with a Device reference to the CMDB, a loan reason and a return date.

Roles

A chain of three roles: admin contains user, which contains requester. I tested every rule with a user who holds only the user role.

Access controls

Requesters can create, read and edit; only admins can delete. A scripted write ACL allows the record’s owner or an app admin, and field ACLs open the description fields to requesters.

Validation

A UI policy makes the return date mandatory for travel loans. A client script rejects past dates as you type, and a before business rule enforces the same rule on the server.

GlideAjax

When a device is picked, the form calls a client-callable Script Include. It counts the device’s active loans with GlideAggregate and the form warns if the device is already out.

Automation

A flow, Prioritize travel loans, runs when a request is created with Travel as the loan reason and raises it to Priority 2 – High, running as the system user. The app also has a CSV import that coalesces on number, and an outbound REST message tested against a demo API.

CASE · 04 · DEBUGGING

Three things that broke

SYMPTOM · CAUSE · FIX · LESSON

BUG 01 · BUILD 1FIXED
symptom

The renumber that said it worked

A background script renumbered 23 old requests and reported 23 updates, but every record still started with TASK.
cause
getNextObjNumberPadded() on the record took its number from the parent table’s counter, not the Loaner Request one.
fix
Named the counter explicitly with new NumberManager('u_loaner_request'), tested on one record with setLimit(1), then ran the rest.
lesson
Check the result, not the row count.
BUG 02 · BUILD 2FIXED
symptom

The date check you could walk around

A past return date was blocked on the form, but the same value saved without complaint when edited from the list.
cause
Client scripts only run on the form. List editing never loads them.
fix
A before business rule with the same check, so the server rejects the save whichever way it arrives.
lesson
Client checks are feedback; the rule itself belongs on the server.
BUG 03 · BUILD 2FIXED
symptom

Fields a requester could not edit

Requesters could write to their own requests, yet Description stayed read-only.
cause
The table extends Task, so it inherits Task’s field ACLs, and task.description requires itil.
fix
Field ACLs on the app’s own table for description and short description.
lesson
Extending a table inherits its security, not just its fields.
CASE · 05 · NEXT

What I’d do next

KNOWN GAPS

  • The closed-request ACL blocks edits but not deletes. A matching delete rule would close that gap.

  • State is not on the Infinity Loaner form, so a fulfiller has to use the board or the list to see it.

  • In Loaner Tracker the requester picks the device. In a real process the fulfiller would assign one from stock, and the “already on loan” check would protect them instead.

  • Most of Build 1 sits in the Default update set; only the last change was captured in a named one. Next time, a named update set from the first change.
